# CheckStock

Небольшой учёт остатков для одного магазина: где лежит артикул, сколько из этого доступно и что уже уехало. Стек: Python, FastAPI, PostgreSQL.

## Запуск

Нужен PostgreSQL 16+ (или контейнер ниже). Пользователь и база по умолчанию: `checkstock` / `checkstock`, база `checkstock`.

```powershell
docker compose up --build
```

Открыть http://127.0.0.1:8000

Если Docker нет, а PostgreSQL уже стоит локально, один раз создать роль и базу:

```sql
CREATE USER checkstock WITH PASSWORD 'checkstock' CREATEDB;
CREATE DATABASE checkstock OWNER checkstock;
```

```powershell
py -m venv .venv
.\.venv\Scripts\python -m pip install -r requirements.txt
$env:DATABASE_URL = "postgresql+psycopg://checkstock:checkstock@localhost:5432/checkstock"
.\.venv\Scripts\python -m uvicorn app.main:app --reload
```

Если порт 5432 занят другим сервером, подставьте свой в `DATABASE_URL`. Тесты берут тот же адрес и подменяют только имя базы на `checkstock_test`.

При первом старте создаются таблицы и тестовый приход: Север / Юг и три артикула из задания. Кнопка «Тестовые данные» возвращает к этому состоянию.

Проверка, что сервер жив: http://127.0.0.1:8000/api/health

## Что прогнать руками

1. На «Остатках» сверить приход: органайзер 10/6, контейнер 5/0, корзина 0/4. Строка сверху должна сказать, что остатки сходятся.
2. На «Отправках» зарезервировать 5 органайзеров на Севере, когда свободно меньше, а на Юге они есть. Запрос отклоняется, Юг показан в ошибке, числа не меняются.
3. Переместить часть органайзеров с Севера на Юг и принять. До приёмки количество в пути, после — на Юге.
4. Зарезервировать органайзеры на Севере и отправить клиенту. Физический остаток и резерв падают, товар появляется «к клиенту».
5. Отправить контейнер по FBO и принять. До приёмки он в пути, после — на маркетплейсе.
6. Сразу после успешной проводки нажать «Повторить подтверждение с тем же ключом». В истории не появляется вторая строка, количества те же.
7. Удалить Юг. Корзины остаются на архивном складе, приход виден в истории, новый приход на Юг отклоняется.

## Автопроверки

Тесты ходят в отдельную базу `checkstock_test` на том же сервере и рабочую базу не очищают.

```powershell
.\.venv\Scripts\python -m pytest
```

Они фиксируют приход из задания, резерв и отправку FBS, перемещение и повторную приёмку, FBO до склада маркетплейса, запрет везти зарезервированное, нехватку на одном ФФ при достаточном общем остатке, повтор ключа и чужое тело на том же ключе, архив склада с остатком, закрытие уже созданного резерва после архивации и гонку двух резервов на один остаток.

## Ключевые решения

Остаток на ФФ — это два числа: физически на складе и резерв FBS внутри него. Доступно считается, а не хранится. В уравнении «приход = склады + в пути + маркетплейс» резерв второй раз не прибавляется: он уже входит в физический остаток.

Перемещение, FBO и отправка клиенту — документы. Отправка уменьшает склад и создаёт строку «в пути». Приёмка меняет статус документа и кладёт количество в место назначения. Второй запрос с новым ключом видит статус «принято» и ничего не добавляет. Повтор с тем же `Idempotency-Key` и тем же телом возвращает сохранённый ответ: ключ и проводка пишутся в одной транзакции, параллельный повтор того же ключа ждёт advisory lock. Чужое тело с тем же ключом отклоняется.

Нехватка считается только по выбранному ФФ. Если на других активных складах товара хватает, ответ это показывает и предлагает явное перемещение. С невыбранного склада количество не снимается. Зарезервированные единицы в доступное не входят, поэтому их нельзя увезти перемещением или FBO.

Удаление ФФ — смена статуса на «архив», не `DELETE`. Строки остатков, резервы и история остаются, в таблице склад помечен. Новые приходы и отгрузки с него закрыты. Уже созданный резерв можно отменить или отправить: это завершение документа, а не новая выдача. Имя сравнивается без регистра через `str.casefold()` в колонке `name_folded`: у PostgreSQL в Docker локаль C, и `lower()` по-русски на неё не полагается. После архивации то же имя можно отдать новому складу, старый остаётся отдельной строкой.

FBS после отправки остаётся «к клиенту». Отдельной приёмки клиентом в задании нет, и товар не должен исчезать из уравнения. FBO после приёмки числится на складе маркетплейса — это не ФФ и в списке складов его нет.

Схема создаётся при старте (`create_all`), без Alembic: для однодневного прототипа так проще поднять стенд. Неотрицательные остатки, «резерв не больше физического» и единственность активного имени держатся ограничениями PostgreSQL. Гонку двух списаний закрывает `SELECT … FOR UPDATE` по строке остатка.

Один магазин и три артикула заданы тестовым приходом. Отдельного справочника товаров нет: задание его не требует.

Черновик учёта и экранов собран с ИИ в Cursor. Складские сценарии после этого прогнаны `pytest` и руками в браузере; формула сверки видна на каждом экране.

## Что записать на видео

3–5 минут с голосом, один сквозной сценарий: тестовый приход, нехватка на Севере при остатке на Юге, перемещение и приёмка, резерв FBS и отправка клиенту, FBO до приёмки, повтор того же подтверждения, удаление ФФ с остатком. Коротко: почему резерв не второй остаток, почему чужой склад не списывается сам, почему удаление — это архив.
